## System and rule map

1. **Player identity.** `resolveGameAnalysisProvenance` uses immutable import-time username + explicit white/black side, and checks that username matches the recorded player (`src/lib/games/analysisProvenance.ts:20`). It does not infer the side from board orientation or current preferences. Unresolved side gives `USER_SIDE_UNRESOLVED`, not guessed data (`extractTrainingMoments.ts:2724`). Import/HTTP validation is covered by the contract audit.
2. **Replay / decision.** chess.js parses the PGN with `strict:false`; verbose history supplies from/to/promotion; setup FEN is extracted from the PGN header (`:316`, `:2701`). `decisionPly` is zero-based relative to imported movetext, including setup games, not absolute game move number. FEN is before the user's actual move. Own mistake uses `ply`; missed opportunity uses opponent `ply+1` and FEN after the opponent's move (`:3398`). Earlier FENs derive from the parsed move history, making immediate repetition claims inspectable. No side reversal was found in this path.
3. **Scan.** Every replayed ply gets before/after evaluation; after score and WDL are reversed to the mover's POV. Both colors are evaluated to produce review data and find opponent mistakes (`:2828`, `:2923`, `:2965`). User candidates require >1 legal move, primary expected-score loss ≥0.03, and an engine best move + PV. If no best PV exists, extraction records partial information and an error. Quiet positions are explicitly eligible; motif tags never filter them (`:3082`).
4. **Missed opportunity.** Only after a meaningful opponent error, inspect the actual next user move by evaluation, not UCI equality (`:3433`). The initial missed-opportunity test uses expected-score tolerance 0.1 (cp fallback100). If it qualifies for lookahead processing, that decision is owned there end-to-end and not extracted again on the user-ply pass (`:3458`). Its final confirmation uses the ordinary coverage threshold0.03. A response within the missed-opportunity tolerance can still be handled as an own mistake on the next ply. There is no general requirement for a unique tactical punishment.
5. **Mistake confirmation.** MultiPV at solution FEN, after-FEN single-PV at the same requested budget, loss rechecked (`:1496`). Nodes double 200k→400k→800k for STANDARD; THOROUGH can reach1.6m. Escalation is driven by qualification disagreement, >0.015 expected-score change (or40cp fallback), proximity to coverage threshold, or changed best UCI. A changed equivalent best UCI triggers more work, not an immediate rejection. At the cap qualification/loss must be stable; exact best identity is not part of the final stability predicate (`:1694–1729`).
6. **Root alternatives.** First accepted-set calculation can reuse confirmation MultiPV (`:2186`). Ordinary verification then analyzes independently. Initial MultiPV5 expands5→10→16 when frontier is not STABLE; max accepted branches16. A MultiPV budget covers the whole search, not one budget per returned line.
7. **Cp frontier.** Sort by reported MultiPV index, require unique roots, contiguous slots, finite comparable scores, and monotone cp loss. Accept everything ≤policy.success.maxCpLoss (default100). If the next move differs by <30cp, expand through the near-equal cluster to at most140cp. If no ≥30cp boundary is found, OPEN; structurally exhausted short bundles can theoretically close with all moves accepted (`acceptanceFrontier.ts:69–180`). However actual adapters mark only a full requested bundle complete (`stockfishClient.ts:127`), making that short-bundle route unreachable from ordinary browser/server evidence. This is a concrete data-contract defect, not a reason to weaken confidence requirements. BEST≤20cp; STRONG≤50cp; other accepted moves GOOD. WDL/maxWinChanceLoss/preserveOutcome/matePolicy are not consulted here.
8. **Independent set confirmation.** A STABLE ordinary engine frontier gets one double-budget confirmation; membership and per-move tier must match independent of order. This correctly fixes the old equal-ranking-order issue (`acceptanceFrontier.ts:184–220`). Pure tier change still yields OPEN; malformed frontier can yield UNSTABLE. No frontier retry budget is connected to THOROUGH's larger mistake-confirmation cap.
9. **Continuation.** Full extraction defaults to maxPlies2: root user choice and one best opponent reply, then MAX_PLIES leaf. Every accepted root branch receives such a reply. Opponent uses MultiPV1 and is not subject to accepted-set double confirmation. Verifier child failures worsen global status even when the root decision has stable evidence (`continuationVerifier.ts:690`, `:1245`). This is a one-decision exercise, not a proof of an entire forced tactic; changing maxPlies would change scope.
10. **Final moment.** Verification status, stable frontier, and original played move absent from accepted set jointly define `trainable` (`extractTrainingMoments.ts:2472`). There is no separate usefulness score/gate beyond these. `confidence=0.98` for VERIFIED is a categorical constant, not calibrated probability (`:2527`). Alternative trainability defaults when verification is disabled are not used in the default full-analysis path.
11. **Persistence / Practice.** Final assessments inherit frontier tiers; branch evidence separately stores cp/WDL gap and preservesOutcome (`:1987–2009`). The contract/Practice audit documents that ordinary known moves trust this tier and unknown moves in a complete canonical node are rejected directly. Candidate validation checks that preservesOutcome is boolean/null (`candidateValidation.ts:630`) and that assessment grade matches frontier tier (`:920–953`); it does not reapply outcome policy. Thus there is no validation guard against that contradiction. The current browser config-version bug can independently block persistence first, but server completion and a corrected browser envelope do not acquire an outcome-policy guard. This makes generation-side policy inconsistencies relevant to user-visible grading.

## What the score actually means

Engine score and UCI WDL are side-to-move; persistence and numeric UI use White POV. The loss function compares before and negated after score with reversed WDL. Ordinary cp polarity and black-user polarity are consistent (`evaluation.ts:10–39`, `extractTrainingMoments.ts:1539`). Explicit mate results should carry winner and distance; tablebase results carry White-POV WDL. “cp loss” for mate currently includes synthetic ±100,000 ordering values; it is not a material/pawn loss.

`winningChance` computes `(W+0.5*D)/(W+D+L)` when WDL exists. That is expected game score, not probability of winning. Without WDL it uses `1/(1+exp(-0.00368208*cp))`; the cp fallback threshold is effectively unreachable when valid scores exist because this smooth probability fallback is always computable (`evaluation.ts:113–132`, `:152–197`). This differs from runtime matched-evidence grading, which leaves chance absent when matched WDL is unavailable (see contract audit).

Stockfish18's pinned source normalizes ordinary cp with `round(100*v/a(material))` and computes WDL from fitted material-dependent logistic parameters; 100cp is calibrated to approximately50% probability of **winning** in engine selfplay at fishtest LTC, not50% expected score or human blitz win probability. At around100cp, the remainder is largely draws, so expected score can be around75%. [Stockfish18 UCI source](https://github.com/official-stockfish/Stockfish/blob/sf_18/src/uci.cpp#L464), [official WDL model](https://github.com/official-stockfish/WDL_model). Therefore the Lichess-style smooth cp transform and Stockfish WDL are different models; switching between them must be explicit. Lichess separately documents its human-game win-percent/accuracy transform. [Lichess accuracy](https://lichess.org/page/accuracy).

Saturation suppression is intentional and reasonable for “did the result deteriorate?” but cannot by itself answer “is this useful human training?” Losing200cp from+1000 to+800 with WDL1000/0/0 gives loss0 and no candidate, while the cp frontier excludes the+800 move if this position was generated from another original mistake. Already-lost positions have the same tension. Relaxing one threshold blindly would increase contradictions, not establish quality.

## Exact outcomes and terminal rules

The continuation verifier correctly checks checkmate, stalemate, insufficient material,50-move and repetition before engine work (`continuationVerifier.ts:264`). The full scan only special-cases immediate threefold after the played move. Stockfish18's terminal UCI update has no PV/WDL; this is normal protocol, not engine failure. [Pinned Stockfish18 terminal output](https://github.com/official-stockfish/Stockfish/blob/sf_18/src/uci.cpp#L569). The integrated test creates the legal setup after `1.f3 e5 2.g4` and analyzes `2...Qh4#`; full extraction rejects instead of returning a completed manifest. It uses a scripted adapter reproducing that protocol, so timing/actual-runtime scope must be established by the coordinator's real probe.

Tablebase probing is optional and only used in continuation verification for≤7 pieces (`continuationVerifier.ts:717`). The tablebase adapter inverts after-move categories to the mover correctly (`tablebase.ts:177`). Cursed wins/blessed losses map to draw; unknown/maybe categories remain UNKNOWN (`:117`). When exact evidence exists, the verifier accepts all best-WDL moves, not only one DTZ-optimal move (`continuationVerifier.ts:416`). More than16 equally optimal choices leads AMBIGUOUS; that's a resource limit, not lack of exact outcome knowledge. Ordinary engine mate lines still pass through synthetic cp frontier logic, so mate distance can affect accepted tiers even though the declared policy says EXACT. Tablebase unavailability intentionally falls back to engine and must remain visible in evidence.

Additional hypothesis requiring a focused test: tablebase completeness is inferred from selected best-known moves and branch count, without enumerating all legal root moves or proving no UNKNOWN move can also preserve the outcome. `bestTablebaseMoves` filters UNKNOWN and `alternativesComplete` only checks the retained count (`:416`, `:826`). Do not yet claim a real provider response exposed this.

History is represented separately from FEN for immediate repetition; standalone engine searches do not receive the actual full game history. Deep future repetition consequences can differ from a search replayed from the game start. This is an explicit reference-comparison question, not proof that every standalone-FEN evaluation is wrong.

## Personal training versus master publication

Master adds separate gates after shared extraction: accepted count1–3, line length1–10, confidence≥0.95, meaningful loss (≥0.03 expected score OR≥80cp), plus trainable/VERIFIED/STABLE (`src/lib/master/ranking.ts:29–69`). These master-specific gates are not applied to personal extraction. The evidence does **not** support saying that a hidden master uniqueness requirement bans all ordinary multi-solution exercises. The shared frontier and tier-stability gates do, however, impose publication-style certainty on every ordinary personal exercise. Whether tier uncertainty should prevent training is a separate product decision.

The current explicit rejection of an accepted original move is sound for a correction exercise: it avoids teaching “your valid move was wrong.” It does not establish that the original candidate scan was wrong; that scan uses a different tolerance and may use stronger/different evidence. Distinct outcomes should be recorded as mistake confirmed, position gradable, original still accepted, exercise not selected.

## Required clean target contract and order of repairs

1. Add one shared rule-exact terminal/outcome evaluator before scan/confirmation/grading engine calls. Represent terminal winner/draw and zero distance explicitly; do not invent mate-zero cp. Regression: White/Black mates and stalemates as the final game ply produce complete analysis and zero loss for a played best terminal result.
2. Choose and version one grading comparison policy across extraction, known and runtime unknown moves. Specify which fields are authoritative: cp, matched WDL expected score, exact mate/tablebase outcome, preserveOutcome, and any cluster expansion. Require every accepted move to satisfy that shared function; missing/mismatched evidence yields unknown, not false certainty. Acceptance and improvement thresholds can differ but must be named separately.
3. Separate mistake evidence, grading coverage, display-tier certainty, and exercise utility. Keep exact membership uncertainty fail-closed for scored exercises unless runtime adjudication is explicitly designed; avoid converting small label drift into a statement that the player did not make an error. Preserve both snapshots and reasons.
4. Make verification budgets explicit and stage-specific. Evaluate whether frontier confirmation needs adaptive retries when only membership/tier changes, with a clear stop budget; do not silently downgrade final verification relative to expensive confirmation. Independent confirmation is useful and should be benchmarked before removing repeated calls.
5. Report `ORIGINAL_MOVE_ACCEPTED`, `FRONTIER_OPEN_AT_CAP`, `FRONTIER_MEMBERSHIP_CHANGED`, `TIER_ONLY_CHANGED`, `CONTINUATION_UNAVAILABLE`, `EXACT_OUTCOME_UNKNOWN`, and qualification-change reasons distinctly. Include achieved depth/nodes/calls, requested budget, history mode, evaluation family and snapshot identity.
6. Keep homepage scan orchestration and full analysis orchestration separate, sharing terminal evaluation, score conversion and grading contract. A partial scan can suggest where to verify; it cannot produce a complete game receipt.

A useful contract separates `DecisionEvidence` (source hash, decision ply, legal FEN, side/history, original move), `OutcomeEvidence` (typed POV/source/budget and score/WDL model), `MoveAssessment` (same policy function, grade/unknown and proof reference), `CoverageEvidence` (enumerated legal set vs bounded search, known rejected moves and unexamined moves), `ExerciseSelection` (confirmed mistake + training purpose), and `ContinuationEvidence` (review explanation vs required graded gate). Names are a proposal, not an implementation authorization.
